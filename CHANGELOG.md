## [Unreleased]

### Added

- Map Legend & Layer Visibility Controls (`packages/web/src/map/MapLegend.tsx`, Phase 5 deliverable 5): a collapsible panel anchored top-left on the map itself (mirroring `NavigationControl`'s top-right zoom/compass position), with one entry per Phase 4 layer -- CTA Rail, Bike / Trail, Cafes / Fitness / Groceries, Divvy Docks -- each a color swatch (reused from that layer's own single source of truth, `packages/web/src/map/layers/legend-entries.ts`) plus a checkbox toggling that layer's visibility (manual only; every layer stays on by default, addressing the map getting visually overwhelming with every layer always on -- Divvy's ~2,050 stations being the sharpest example). CTA Rail's swatch is a 2-dot cluster (Red + Blue) rather than all 8 lines; POI Density's is a 3-dot cluster (cafe/fitness/supermarket); Bike / Trail adds a small "Protected" (thick solid) / "Shared lane" (thin dashed) mini-key explaining `ProtectedBikeLayer.tsx`'s real width/dash tiers, which a flat swatch color alone couldn't convey; Divvy Docks renders as a split blue/grey circle matching `divvyMarkerIcon.ts`'s real two-tone marker exactly, rather than a flat swatch that would've undone the reason that marker is two-tone in the first place (Divvy's brand blue sits under 1° apart in hue from CTA Blue Line's -- the split *pattern* is what disambiguates it). Each of the 4 Phase 4 layer components (`CtaRailLayer`, `ProtectedBikeLayer`, `PoiDensityLayer`, `DivvyDockLayer`) gains a new optional `visible` prop (new shared `packages/web/src/map/layers/useLayerVisibility.ts` hook) toggling MapLibre's own `visibility` layout property on their underlying layers -- hiding a layer this way also correctly suppresses its hover popups for free, since MapLibre doesn't fire feature-interaction events against a non-rendered layer.
- Weight Customization Slider Drawer (`packages/web/src/components/WeightDrawer.tsx`, Phase 5 deliverable 2, `docs/PRD.md` §3.4): a collapsible drawer with one slider per active factor, plus Remote Worker / Hybrid Commuter preset chips (highlighted when the current weights match one exactly, "Custom" otherwise). Dragging a slider redistributes the freed or absorbed weight proportionally across the other 8 (`packages/web/src/lib/weights.ts`'s `redistributeWeights`, largest-remainder apportionment so the set always sums to exactly 100), and always leaves the dragged slider at exactly the value the user chose. `commute` is deliberately excluded from the drawer (`WEIGHT_FACTOR_ORDER`) -- no destination-entry UI exists anywhere in the app yet to ever activate it, so a commute slider would let a user "weight" a factor that can never actually score; the two presets' PRD-documented `commute` weight is dropped and the remaining 9 renormalized to 100 (`weightsForPreset`), per the PRD's own "Dynamic Normalization" rule. Weights sync live to the URL as flat, human-readable query params (`?w_transit=35&w_grocery=25...`, `packages/web/src/lib/weight-search-params.ts`) via a `validateSearch` added to the root route (`packages/web/src/routes/index.tsx`) -- a fresh visit with no `w_*` params defaults to the Remote Worker preset; any `w_*` param present reads every factor from the URL independently (a missing or garbage value reads as 0, not the preset default) and renormalizes the set, keeping a shared link a complete, self-contained snapshot. A slider move debounces (400ms, `packages/web/src/lib/useDebouncedValue.ts`) before re-scoring the already-resolved address's exact coordinates directly -- no re-geocode -- via a new App-level `useMutation` (`App.tsx`); the Hero Ring and Factor Breakdown Cards dim slightly (`opacity-60`) while a rescore is in flight. Also threads the current weights into `AddressSearchInput`'s own initial score request (new optional `weights` prop) so a pre-adjusted weighting -- from the URL, or set before the first search -- applies from the very first score rather than only catching up once a slider is touched.
- Factor Breakdown Cards (`packages/web/src/components/FactorBreakdownList.tsx`, `packages/web/src/components/ui/factor-card.tsx`, Phase 5 deliverable 2, `docs/ARCHITECTURE.md` §7.3 "Factor Breakdown Accordions"): one accordion row per scored factor, rendered below the Hero Composite Score Ring in `docs/PRD.md` §4's fixed weighting-table order (`transit`, `commute`, `bike`, `grocery`, `thirdPlace`, `green`, `noise`, `safety`, `flood`, `solar`) via a new `packages/web/src/lib/factor-metadata.ts` (label + Lineicons icon per factor). `commute` renders only when the API response includes it (a destination was supplied). Each row shows a tier-colored sub-score progress bar (reusing `ScoreRing`'s `scoreTier` boundaries), an "Unavailable" badge instead of a bar when the factor is `degraded`, and a straight-line-qualified distance pill (new `packages/web/src/lib/format.ts`, `formatDistanceMiles`) when `distanceMeters` is present. Rows with `contributingPois` are click-expandable to reveal each POI's name and distance, collapsed by default to keep the list dense. Replaces `App.tsx`'s previous ad hoc solar-only sidebar chip, which this supersedes for every factor including solar.
- Hero Composite Score Ring (`packages/web/src/components/ui/score-ring.tsx`, Phase 5 deliverable 2): a circular SVG progress ring around the resolved address's composite score, colored by the same score tier a `Badge` would use (`stroke-emerald/lime/amber/rose-400`, matching `Badge`'s own score-* variant colors exactly rather than the currently-unused `--color-score-*` theme tokens). Replaces the sidebar's plain `81 / 100` text. Hand-rolled SVG (`stroke-dasharray`/`stroke-dashoffset`) rather than a charting library, since a single arc doesn't need one.
- `addressHint` field on `POST /api/v1/score`'s `ScoreRequest` (`docs/openapi.yaml`): an always-optional string, ignored when `address` is set, used only for `S_solar`'s street-facing orientation inference when scoring by pre-resolved `origin` coordinates — never triggers a geocoding call. Fixes the redundant-geocode latency regression noted under Fixed below.

- Water bodies on the map (Lake Michigan, the Chicago River) now render in `#5c8da0` instead of `dark-matter-gl-style`'s own near-black default (`#2C353C`, verified by fetching the live style JSON), via `map.setPaintProperty("water", "fill-color", ...)` once the basemap loads (`packages/web/src/map/MapCanvas.tsx`, new `WATER_FILL_COLOR` constant).

- Header wordmark (`packages/web/src/App.tsx`): "Block" and "Factor" now split-colored in the Chicago flag's blue and red (`--color-flag-blue`/`--color-flag-red`, `index.css`). The 1917 municipal ordinance only describes the flag's colors qualitatively ("sky blue", "bright red") -- there's no single official numeric hex -- so these use the most consistently-cited pairing across dedicated flag-color references (`#41b6e6`/`#ef002b`), verified via web search rather than assumed. `--color-flag-blue` intentionally matches the existing `--color-divvy-blue` value (Divvy's own branding is itself Chicago-flag-derived) but stays a separate token since it means something different here.

- Address Search & Geocoding Input (`packages/web/src/components/AddressSearchInput.tsx`, `docs/IMPLEMENTATION_PHASES.md` Phase 5 deliverable 1): the first real user-supplied-address entry point anywhere in the app, replacing the fixed 233 S Wacker Dr demo coordinate (`DEMO_ADDRESS_LAT`/`LON`/`FACING`, now removed) every Phase 4 map layer queried against. Submitting an address calls `GET /api/v1/geocode`; zero candidates shows a "no address matched" notice, one candidate auto-resolves, and 2+ shows a ranked picker list. Once resolved, `POST /api/v1/score` scores the coordinate — a `422 OUT_OF_COVERAGE` response shows a dedicated notice, any other scoring failure a generic one. The resolved address becomes the app's active coordinate: the map flies to it, the POI Density Layer re-queries around it (rendering only once an address has resolved, rather than always querying the old fixed coordinate), and the sidebar swaps its composite-score placeholder for the real `compositeScore` plus the solar exposure badge (now driven by the scored `factors.solar` value instead of a client-computed orientation guess). Before any search, the sidebar shows an explicit "search an address" prompt rather than silently scoring a stand-in address. `packages/web/src/map/layers/solarScore.ts`'s `solarScoreTier` is renamed to `scoreTier` and reused for both the solar and composite score badges, since the tier mapping was never solar-specific.
- CTA Rail Layer (`packages/web/src/map/layers/`): official per-line CTA colors and interactive station hover cards on the map, fed by the `/api/v1/layers/cta-rail` and `/api/v1/layers/cta-stations` endpoints via TanStack Query. A track segment shared by 2+ CTA lines (real cases confirmed up to 5) renders as one thin colored line per line, evenly offset around the segment's centerline (`line-offset`), rather than one line's color hiding the others; subway (underground) segments render dashed, elevated/at-grade solid. Station hover cards show the station name, real CTA line color badges, and ADA accessibility status (Lineicons `lni-wheelchair-1`). Also fixes a real, previously-uncaught bug in `packages/web/src/lib/api/client.ts`: `baseUrl: "/api/v1"` combined with `schema.d.ts`'s already-full-path keys was double-prefixing every request to `/api/v1/api/v1/...` — nothing had called `apiClient` yet, so this is the first PR to actually exercise it.
- Protected Bike Layer (`packages/web/src/map/layers/ProtectedBikeLayer.tsx`, Phase 4 deliverable 5): a high-visibility green (`#10b981`, deliberately distinct from CTA Green Line's `#009b3a`) linestring overlay for street bike infrastructure, fed by `/api/v1/layers/bike-routes`, with line width/opacity/dash weighted by the real quality gradient across `routeType` — protected/buffered lanes render bolder and solid, painted-only `Marked Shared Lane` ("sharrow") segments render thin and dashed since they're a paint marking, not a dedicated facility. Also renders off-street trail access (the Lakefront Trail, The 606) as a translucent fill + outline from `/api/v1/layers/trail-access`, with a hover card showing the trail name.
- `GET /api/v1/places?lat=&lon=` (Phase 4 deliverable 6, `docs/ARCHITECTURE.md` Decision Log row 30): nearby cafes, fitness venues, and supermarkets as a GeoJSON `FeatureCollection`, scoped to a fixed 0.5 mi per-address radius rather than a city-wide bulk layer — the same radius, and the exact same Google Places grid cache, `S_third_place` itself scores against. Extracts `ThirdPlacePoiResolver` out of `internal/scoring/factor_third_places.go` (the cache-fill/lookup logic, previously inlined in `ThirdPlaceCalculator`) so one shared instance — one `singleflight.Group`, one daily budget counter — serves both the scoring path and this endpoint, genuinely deduplicating a concurrent request to each for the same grid cell rather than each independently spending budget. Adds `internal/scoring/places.go` (`NearbyPlacesResolver`, blending the shared resolver with a radius-scoped `osm_pois` supermarket query reusing `GroceryQuerier`) and `internal/api/places.go` (`PlacesFinder` interface + handler, following the same api-owned-types/`cmd/server`-adapter pattern as `ScoreEngine`). `OsmPoi` (`factor_grocery.go`) gains `Lat`/`Lon` fields, additive and unused by `S_grocery`'s own scoring, needed here to place a marker. Requests outside the City of Chicago boundary are rejected with 422 `OUT_OF_COVERAGE` to avoid spending Places API budget on out-of-coverage coordinates. Verified live end-to-end against real Chicago Places/OSM data — also caught and fixed a real classification bug during that verification: Google Places (New) can return a result whose `primaryType` isn't actually one of the requested `includedTypes` (a hotel or fast-food restaurant with a gym/cafe amenity), which an earlier version of this endpoint defaulted straight into `"fitness"` instead of excluding.
- `GET /api/v1/layers/divvy-docks` (Phase 4 deliverable 8): live Divvy/Lyft bike-share dock locations and availability as a GeoJSON `FeatureCollection` — display-only, not a scored factor. Unlike every other `/layers/*` endpoint, this isn't bulk-ingested PostGIS data; it's the public GBFS 2.3 feed (`station_information.json` + `station_status.json`, verified live rather than assumed from the spec name — `is_renting`/`is_returning` come back as `1`/`0` integers, not real JSON booleans), joined by `station_id` and served through a new `internal/clients/divvy.go` (`DivvyClient.FetchStations`, retried with exponential backoff mirroring `OverpassClient`/`PlacesClient`) plus a 5-minute in-process TTL cache (`DivvyStationsCache`, `docs/ARCHITECTURE.md` §5.4 — deliberately not Postgres/Redis, keeping this dependency-free) — confirmed live: repeat requests drop from ~400ms (two real upstream fetches) to ~16ms (served from cache). A refresh failure with a previous successful fetch already cached logs a warning and keeps serving the stale value rather than erroring; only a cold start with no prior fetch returns 502 `DIVVY_UNAVAILABLE`. `internal/api/divvy.go` (`DivvyDocksReader` interface + handler) and `cmd/server/divvy_adapter.go` follow the same api-owned-types/adapter pattern as `ScoreEngine`/`PlacesFinder`. Wired unconditionally in `cmd/server/main.go`, independent of `DATABASE_URL` — genuinely the only backend feature with zero Postgres dependency. Verified live end-to-end against the real feed: all 2050 real Chicago-area stations, correct join, correct `isRenting`/`isReturning` including a real currently-closed-for-rebalancing station.
- Divvy Dock Layer (`packages/web/src/map/layers/DivvyDockLayer.tsx`, Phase 4 deliverable 9): live bike-share station markers with a live bikes-available count badge, fed by `/api/v1/layers/divvy-docks` — display-only, not a scored factor. Markers are a two-tone split icon (new `DESIGN.md` "Divvy Dock Markers": Divvy's real brand blue `#41b6e6` + `text-secondary` zinc-400 standing in for the grey on Divvy's retroreflective e-bike fleet, no verified digital hex exists for that physical coating) rendered via the Canvas API and registered with `map.addImage` — a flat single-color dot was ruled out up front this time: Divvy Blue sits under 1° apart in hue from CTA Blue Line's `#00a1de` (computed HSL, not eyeballed), so the split *pattern* itself is what disambiguates the layer, not the hue alone. The bikes-available badge uses `dark-matter-gl-style`'s own confirmed-working font stack (verified against the basemap's live style JSON, since an unavailable `text-font` silently fails to render) and MapLibre's default text collision detection, so 2050 real stations stay readable at every zoom without extra work; markers themselves always render (`icon-allow-overlap: true`, matching how `circle`-layer markers elsewhere have no collision system to opt out of), and dim (not disappear) when a station is installed but not currently renting/returning.
- Solar Exposure Badge (`packages/web/src/App.tsx`, Phase 4 deliverable 10, the final Phase 4 deliverable): a plain sidebar `<Badge>` (e.g. "W-Facing · 75") showing the scored unit's window-facing orientation and its real `S_solar` base score (PRD §5.8), colored by score tier (new `DESIGN.md` "Solar Exposure Badge" — reuses the existing `score-emerald`/`lime`/`amber`/`rose` tiers, the correct semantic fit here since this badge genuinely represents a score, unlike the POI/Divvy category markers). Two earlier iterations tried a 3D `fill-extrusion` ray on the map itself — first a flat gold wedge encoding only direction, then colored/sized by score tier — but live review found a novel 3D shape plus a color-tier meaning plus a compass direction, all at once with no on-screen legend, still wasn't clear at a glance; the score moved to the sidebar's plain badge language instead of asking the map scene to carry it alone. `packages/web/src/map/layers/solarScore.ts`'s `solarBaseScore`/`solarScoreTier` are pure functions, no backend call; the demo facing (`DEMO_ADDRESS_FACING = "W"`) was verified by actually running `InferStreetFacingOrientation` against the exact demo address rather than guessed.
- POI Density Layer (`packages/web/src/map/layers/PoiDensityLayer.tsx`, Phase 4 deliverable 7): cafes, fitness venues, and supermarkets around a coordinate from `/api/v1/places`, plus two muted (`zinc-500`, dashed) distance reference rings at half and full search radius — deliberately not an accent color, since a spatial reference guide isn't scored data. POI markers are color-coded per category (new `DESIGN.md` "POI Category Markers" tokens: `poi-cafe` copper `#c2703d`, `poi-fitness` indigo `#6366f1`, `poi-supermarket` teal `#0d9488`) rather than a neutral dot, and hover cards additionally show a matching Lineicons glyph (`lni-coffee-cup-2` / `lni-dumbbell-1` / `lni-basket-shopping-3`, verified against the installed package) — an initial version reused CTA stations' neutral zinc-dot styling and was indistinguishable from station markers on the map itself, caught via live review. New `DESIGN.md` "Category Color Independence Rule": these `poi-*` tokens are dedicated and never reused from the CTA line or `score-*` tier palettes, since a POI marker rendered in an existing `score-*` hex would misleadingly read as a livability score for that specific place. Queries around a fixed demo coordinate (`packages/web/src/map/constants.ts`, `DEMO_ADDRESS_LAT`/`DEMO_ADDRESS_LON` — the same 233 S Wacker Dr point `docs/openapi.yaml`'s own `/score` example and the Go test suite already use) rather than a real selected address, since there's no address-search UI yet (`docs/IMPLEMENTATION_PHASES.md` Phase 5 deliverable 1) — chosen over refetching on map pan/move specifically to avoid uncapped Google Places spend against the shared daily budget from idle map exploration.
- Five read-only map layer endpoints (`GET /api/v1/layers/{cta-rail,cta-stations,bike-routes,trail-access,supermarkets}`), each returning a bulk, city-wide GeoJSON `FeatureCollection` built server-side in Postgres (`jsonb_build_object`/`jsonb_agg` + `ST_AsGeoJSON`, via the new `internal/spatial.LayerReader`) rather than assembled in Go — the handler writes the already-correct JSON bytes straight through. `trail-access` reads `parks WHERE park_class = 'LINEAR PARK'` (the Lakefront Trail, The 606), not `bike_routes`, which has no trail category. Verified live end-to-end: all 5 endpoints return exactly the row counts independently confirmed against each source table (153/144/1008/22/273).
- `--dataset=cta_rail_lines`: ingests the Chicago Data Portal's per-line CTA 'L' rail track geometry (`xbyr-jnvx`) into a new `cta_rail_lines` table (migration `00016`), powering the Phase 4 CTA Rail map layer — the first source of real per-line track geometry (`cta_stops` only has station points; `noise_sources`' CTA track geometry is line-agnostic). Parses the source's messy comma-separated `lines` field (inconsistent `"(Express)"`/`"(Exp)"` abbreviation, Blue Line's two non-express branch qualifiers) into a `TEXT[]` matching `cta_stops.lines`'s vocabulary plus a separate `express BOOLEAN`, and maps its `type` field to a coarser two-way `grade` (`subway` / `elevated_or_at_grade`) distinct from `noise_sources`' three-way grade split. Verified live: all 153 rows load with valid geometry, matching the confirmed 132/21 grade split and 16 express segments.
- Phase 4 map foundation (`packages/web/src/map/`): GPU-accelerated MapLibre GL JS canvas (`maplibre-gl@^5.19.0`) replacing the Phase 1 placeholder card, using CARTO's free, keyless `dark-matter-gl-style` vector basemap centered on Chicago. The map panel is now responsive (fixed height on mobile, sticky full-bleed height on desktop) and releases its WebGL context on unmount (`map.remove()`) to avoid a context leak. Exposes an `onMapReady` callback so later Phase 4 layer PRs (CTA rail, bike routes, POIs, Divvy docks, solar ray) can attach sources/layers to the live map instance.
- `S_third_place` scoring factor (PRD §5.4): cafes and fitness venues within a 0.5 mile radius, scored 100/75/40/0 by count and proximity, with independent cafes (vs. chain brands like Starbucks/Dunkin', via a maintained exclusion list) weighted separately from fitness venues per the PRD's benchmark tiers. Adds `internal/clients/places.go` (Google Places API (New) `searchNearby` client) and `internal/scoring/factor_third_places.go`, which fills the existing `cache_entries` grid cache (400m cells, 30-day TTL, keyed by coordinate per `PRIVACY_AND_DATA_HANDLING.md` — never the raw address) with `golang.org/x/sync/singleflight` deduplicating concurrent cache-fills for the same cell. A new `places_api_budget` table (migration `00015`) enforces a daily cap on Places API calls, atomically incremented in Postgres rather than in-process memory so the cap survives restarts/redeploys and holds correctly across multiple server instances; exceeding it degrades `S_third_place` to `null` for the rest of the day rather than erroring the score request. Adds `GOOGLE_PLACES_DAILY_BUDGET_CALLS` to `.env.example`.
- `S_commute` scoring factor (PRD §5.10): scores a rush-hour ("next Tuesday 8:30 AM", America/Chicago) door-to-door transit itinerary to an optional user-provided workplace destination, banded 100/85/55/25/0 by duration plus a +10 one-seat-ride bonus and a -15/transfer friction penalty beyond the first transfer. Adds `internal/clients/otp.go`, defining `Itinerary`/`Leg`/`Route` types shaped after OpenTripPlanner 2's real GTFS GraphQL API (`planConnection` query, verified against OTP2's own schema) — Phase 3 scope is these types plus `internal/scoring/factor_commute.go`'s interface and fixture-tested scoring logic only; the live GraphQL-calling client lands in Phase 6.
- `POST /api/v1/score` (PRD §5.1): the composite scoring endpoint, wiring all 9 always-active factor calculators (transit, bike, grocery, third place, green, noise, safety, flood, solar) plus `S_commute` through `internal/scoring/engine.go`. Resolves `address`/`destination` via the existing Nominatim geocoder (best-ranked candidate) or accepts pre-resolved `origin`/`destinationCoordinates` directly, rejects requests outside the City of Chicago boundary with 422 `OUT_OF_COVERAGE`, and returns 400 `VALIDATION_ERROR` for a missing/duplicated address-or-origin or destination-or-destinationCoordinates pair. `S_commute` is registered with a `nil` querier (no live OTP2 client exists until Phase 6): it correctly appears in the response as `degraded: true` whenever a destination is supplied, rather than silently vanishing, and `benchmarkCommutes` is an honest empty array until Phase 6 can compute real hub pills. Adds `api.ScoreEngine` (`internal/api/score_engine.go`), a narrow interface expressed in `api`-owned types so the `api` package can depend on the scoring result shape without importing `internal/scoring` directly — `internal/scoring` already imports `internal/api` for its own request/response types, so the reverse import would be a cycle; `cmd/server`'s new `scoreEngineAdapter` bridges the two. Verified live end-to-end against the real Postgres/PostGIS data, Nominatim, and Google Places API for a real Chicago address.

Adds `bike` to `WeightOverrides` and `ScoreResponse.factors` in the OpenAPI contract, and rebalances the default weight presets (PRD §3.4) to include it.

- `S_safety` crime taxonomy (PRD §5.9): `cpd_crimes.category` expanded from a `violent`/`property` split to four scored categories (`violent`, `sexual`, `property`, `nuisance`), with a fifth unscored "excluded" set dropped at ingestion. `safety_grid_percentiles` now stores raw per-category counts alongside the combined `penalty_score`. Full `primary_type`/`iucr` mapping verified against the live Chicago Data Portal API (see `docs/DATA_SOURCES.md` "Category coverage").
- Data ingestion CLI (`services/api/cmd/seed`), first working dataset: `--dataset=boundary` fetches Chicago's city limits from the Chicago Data Portal and loads it into `city_boundary`, replacing the table's single row on each run. Adds the generic building blocks every later dataset PR reuses: a Socrata (SODA) API client (`internal/clients`, `X-App-Token` auth) and a PostGIS connection pool (`internal/spatial`, via `pgx/v5`).
- Three more seed CLI datasets: `--dataset=cta` groups the Chicago Data Portal's per-directional-platform rows into one `cta_stops` row per physical station (unioning line flags); `--dataset=bike_routes` and `--dataset=parks` load their respective datasets directly via `ST_GeomFromGeoJSON`. `--all` now runs all four implemented datasets in one pass. Parks are also repaired with `ST_MakeValid()` on ingest — 11 of 617 source park boundaries (including Washington Park, Grant Park, and Lincoln Park) have self-intersecting rings, a real data-quality issue in the source shapefile, not an ingestion bug.
- `--dataset=crimes`: ingests the trailing 12 months of Chicago crime data (~225K rows) into `cpd_crimes`, classified via the `S_safety` taxonomy (PRD §5.9). Pages through the source via `id`-based keyset pagination rather than `$offset` (confirmed via Socrata's own docs and the dataset's column metadata — see `docs/DATA_SOURCES.md` "Crimes" "Pagination"). The full fetch happens before any database transaction opens, so the `TRUNCATE` + batched-insert transaction that follows is seconds long rather than spanning the ~80s, 45-request fetch. Rows with no coordinates (~0.03% of the source) are skipped; a `primary_type`/`iucr` combination outside the documented taxonomy is logged as unrecognized and skipped rather than guessed. `internal/clients.SODAClient.GetJSON` now retries transient failures (network errors, 429, 5xx) with exponential backoff, benefiting every dataset.
- `--dataset=osm_pois`: ingests supermarkets, convenience stores, and pharmacies into `osm_pois`, powering `S_grocery`. Uses the live Overpass API (`internal/clients/overpass.go`) rather than the originally-planned local `.osm.pbf` file + `ogr2ogr`, after live verification found the local path lost the source ID for 99.8% of way-mapped (building-outline) stores — a real, non-trivial gap, since 52% of Chicago's real supermarkets/pharmacies turned out to be way-mapped rather than node-mapped. See `docs/DATA_SOURCES.md` "OSM POIs" and `ARCHITECTURE.md` Decision Log row 26 for the full investigation. Adds `internal/cache`, a generic Postgres-backed (`cache_entries`) key-value cache with a TTL — used here to cache the Overpass response (24h) rather than a local file, chosen specifically for portability across deployment environments; the same table will back Phase 3's Google Places grid cache later.
- `--dataset=noise`: ingests CTA rapid-transit tracks, expressways, and arterial roads into `noise_sources`, powering `S_noise`. Also via Overpass (`out geom` for full line geometry). CTA track grade (elevated/at-grade/underground) is derived from `tunnel`/`bridge`/`layer` tags rather than the `railway=subway` tag itself, which turned out to be used for the whole CTA system regardless of actual grade — verified against all 1,842 real track ways, including a spot-check confirming a way literally named "South Side Elevated" classifies correctly as `elevated`, not `underground`. `noise_sources` also gains `lanes`/`maxspeed_mph`/`has_turn_lane` columns, captured now (best-effort, nullable) for a planned future `S_stroad` / Street Safety factor rather than requiring a re-ingest later — see PRD §5.6.
- `--dataset=flood_zones`: ingests FEMA's National Flood Hazard Layer into `fema_flood_zones`, powering `S_flood`'s base score. Requires `city_boundary` to already be populated (run `--dataset=boundary` first) and fails loudly rather than silently ingesting zero rows if it isn't. Uses FEMA's own live ArcGIS REST MapServer (`internal/clients/fema.go`, `hazards.fema.gov`) rather than a downloaded shapefile/GDB extract, verified end-to-end before committing to it over the bulk-download path. `FEMAClient.QueryLayer` pages adaptively, ordered by `OBJECTID` for a stable, non-overlapping sequence across pages — halving the attempted window size on a size-related 5xx and retrying the same offset — since NFHL's vertex-dense polygons hit a server-side response-size ceiling independent of the row-count limit, deterministically rather than transiently (confirmed live: the same offset failed at one page size and succeeded at a smaller one, every time). A rate limit (429) or network failure instead gets ordinary exponential backoff at the same window size, and `FEMAClient.Count` now retries transient failures too, matching `QueryLayer`. A real undocumented zone value, `FLD_ZONE = "OPEN WATER"` (marks literal water bodies, not a risk-rated parcel), is logged and skipped rather than guessed into the official 10-code standard, as is a duplicate `FLD_AR_ID` (defense in depth alongside the `OBJECTID` ordering). Flood zone polygons are also repaired with `ST_MakeValid()`, same as `parks.go` — 1 of 291 Chicago-area zones had a self-intersecting ring. See `docs/DATA_SOURCES.md` "Flood Zones" and `ARCHITECTURE.md` Decision Log row 27.
- `--dataset=sewer_311`: ingests trailing 24 months of 311 water/sewer backup complaints (`sr_type = 'Water in Basement Complaint'`) from the Chicago Data Portal (`v6vf-nfxy`) into `sewer_311_incidents`, powering the localized urban flood penalty in `S_flood` (PRD §5.7). Pages via `sr_number` keyset pagination (~25.8K rows across ~6 SODA requests, < 10s fetch). Filters out `duplicate = true` rows (~4.4% of records) which represent redundant citizen reports for the same ongoing incident, avoiding multiplied penalties for a single event. Missing coordinate rows (~0.04%, 12 rows) are skipped; valid rows are loaded via a single fast `TRUNCATE` + batch insert transaction. Tested live against PostgreSQL with verified GiST spatial index performance.
- `--dataset=safety_grid` (and `--dataset=derive`): derives the ~500m citywide crime penalty distribution into `safety_grid_percentiles`, powering $S_{\text{safety}}$ percentile normalization (PRD §5.9). Projects `city_boundary` to UTM Zone 16N (`EPSG:32616`) to generate 2,650 uniform 500m square cells via PostGIS `ST_SquareGrid`, joins ~225K records from `cpd_crimes`, sums category counts, calculates raw penalty scores, and computes cumulative distribution percentiles via `PERCENT_RANK()`. Implements a zero-downtime recompute pipeline (ARCHITECTURE §11.3) writing derivations into an `UNLOGGED` staging table before performing an atomic transactional swap (~20ms lock duration) to prevent blocking live scoring queries.
- `--dataset=bus_corridors` (and `--dataset=derive`): derives CTA bus corridor geometries and scheduled headways into `bus_corridors`, powering the $+10\text{ pt}$ bus proximity bonus in $S_{\text{transit}}$ (PRD §5.2) and full network rendering for Phase 4 map layers. Streams the official CTA Static GTFS Schedule archive (`google_transit.zip`) in-memory using Go standard library (`archive/zip` + `encoding/csv`), parses weekday active services (`calendar.txt`), and computes scheduled mean headways per route across active directions during the weekday AM rush hour window (7:00–9:00 AM) from `trips.txt` and `stop_times.txt`. Routes meeting the $\le 10\text{ min}$ mean headway threshold (112 of 125 routes in live CTA data) qualify as high-frequency corridors, while off-peak/night routes receive a `999.00` sentinel. Assembles physical alignments from `shapes.txt` into composite `MULTILINESTRING` geometries in WGS84 (`EPSG:4326`) `geography` for all 125 Chicago bus routes. Caches the raw GTFS zip in `cache_entries` (PostgreSQL) with a 90-day TTL matching CTA's quarterly seasonal schedule cycle, speeding up subsequent development seed runs to ~4 seconds while remaining stateless in ephemeral containers. Implements a zero-downtime recompute pipeline via `bus_corridors_staging` and an atomic transaction swap (~170ms lock duration).
- Outbound Nominatim geocoding client (`services/api/internal/clients/nominatim.go`): one-shot address geocoding returning ranked coordinate candidates, rate-limited to $\le 1\text{ req/sec}$ via `golang.org/x/time/rate` with exponential backoff on transient errors (429, 5xx) and compliant `User-Agent` headers per the Nominatim Usage Policy. Biases candidate queries to the greater Chicago metropolitan area via viewbox.
- PostGIS city boundary spatial check (`services/api/internal/spatial/boundary.go`): verifies whether coordinate pairs fall inside the `city_boundary` multi-polygon via `ST_Covers(geom::geometry, ST_SetSRID(ST_MakePoint(lon, lat), 4326))`, enabling early rejection of out-of-coverage scoring requests.
- `GET /api/v1/geocode` HTTP handler (`services/api/internal/api/handlers.go`): wires address resolution to the Nominatim client, returning typed OpenAPI `GeocodeResponse` candidates with input query validation.
- Scoring engine orchestrator and weight normalizer (`services/api/internal/scoring/engine.go`): coordinates concurrent factor calculations, dynamically normalizes active weights ($\sum w_i = 100\%$) across default presets (Remote Worker vs. Hybrid Commuter) and user overrides, implements graceful degradation for timed-out or missing factor data, and clamps sub-scores to $[0, 100]$.
- $S_{\text{solar}}$ solar exposure factor (`services/api/internal/scoring/factor_solar.go`): computes natural lighting quality from window orientation lookup (South 100 to North 40 with intermediate interpolations), exposure modifiers (street $1.0\times$, courtyard $0.65\times$, alley $0.50\times$), and floor level bonuses ($+5\text{ pts}$ per floor above floor 2).
- Automatic street-facing orientation inference (`services/api/internal/scoring/orientation.go`): automatically derives a building's true street-facing window direction from Chicago's 1909 Brennan address numbering system (odd numbers on East-West streets face North, even numbers face South; odd numbers on North-South streets face West, even numbers face East; with diagonal azimuth geometry) when unit-level metadata is omitted.
- $S_{\text{flood}}$ flood risk factor (`services/api/internal/scoring/factor_flood.go`): evaluates FEMA National Flood Hazard Layer polygon overlays (Zone X 100 pts vs. Zone A/AE 40 pts) and applies a localized urban sewer backup penalty ($-5\text{ pts}$ per 311 basement flooding complaint within $0.25\text{ mi}$ over trailing 24 months).
- $S_{\text{noise}}$ acoustic livability factor (`services/api/internal/scoring/factor_noise.go`): calculates cumulative proximity penalties from quiet street baseline (100 pts) for elevated/at-grade CTA tracks (-35 pts at < 150 ft, -20 pts at 150–300 ft; subways exempt), expressways (-30 pts at < 500 ft), and major 4-lane arterials (-15 pts at < 100 ft).
- $S_{\text{grocery}}$ grocery and daily retail factor (`services/api/internal/scoring/factor_grocery.go`): computes supermarket distance decay (100 pts at <= 0.3 mi, 75 pts at 0.3–0.75 mi, linear decay to 0 at 1.0 mi), corner store/convenience fallback (capped at 40 pts), and pharmacy bonus (+10 pts at <= 0.2 mi).
- $S_{\text{green}}$ green space and parks factor (`services/api/internal/scoring/factor_green.go`): evaluates geodesic distance to nearest park polygon boundary (100 pts at <= 0.1 mi, decaying to 50 pts at 0.3 mi and 0 pts at 0.75 mi) plus signature linear trail bonus (+15 pts for Lakefront Trail, The 606/Bloomingdale Trail, or `LINEAR PARK` at <= 0.25 mi).
- $S_{\text{safety}}$ public safety factor (`services/api/internal/scoring/factor_safety.go`): evaluates localized point-in-polygon crime incident density against precomputed citywide ~500m grid percentiles (`safety_grid_percentiles`), mapping relative safety percentiles cleanly to intuitive 0–100 scores (100.0 - percentile).
- $S_{\text{bike}}$ bike infrastructure factor (`services/api/internal/scoring/factor_bike.go`): calculates quality-tiered proximity decay to cycling infrastructure (100 pts for Protected Bike Lanes/Greenways, 70 pts for Buffered Lanes, 40 pts for Painted Lanes, 15 pts for Sharrows; decaying to 0 at 0.5 mi) and awards a +15 pt dual-axis network bonus for connectivity across both North-South and East-West corridors.
- $S_{\text{transit}}$ transit accessibility factor (`services/api/internal/scoring/factor_transit.go`): calculates distance decay to CTA 'L' rapid-transit stations (100 pts at <= 0.25 mi, linear decay to 0 pts at 1.0 mi) and awards a +10 pt bonus for dual-line station access (2+ distinct lines across stations within 1.0 mi) or high-frequency bus corridors (mean headway <= 10 min) within <= 0.2 mi.
- `cta_line_service` table (`db/migrations/00014_create_cta_line_service.sql`): one row per CTA 'L' line storing AM-peak and overnight mean headway, powering the revised $S_{\text{transit}}$ rail service-quality bonus (PRD §5.2).
- `--dataset=cta_line_service` (and `--dataset=derive`): derives per-line AM-peak and overnight headway into `cta_line_service` from the same CTA static GTFS feed already used for `bus_corridors` (`route_type = 1` rather than `3`), reusing its weekday-service parsing for the AM-peak pass and adding a new any-day-of-week (but still validity-window-filtered) pass for the 1:00-4:00 AM overnight window per PRD §5.2. `line_name` is derived from `route_long_name` (e.g. `"Red Line"` → `"Red"`) rather than `route_id`, which is inconsistently formatted across lines. The overnight pass weights each contributing `service_id` by how many nights per week it actually runs (`computeOvernightHeadwaysByLine`) rather than naively summing trips across every weekday/Saturday/Sunday template — CTA's real feed splits overnight service into several such templates per line, and summing them unweighted inflated a single night's trip count by up to ~3x (caught in review before merge; see `docs/DATA_SOURCES.md` "CTA Line Service" for the live-verified numbers). No staging-table swap (8 rows, no geometry) and no `geom` column, unlike `bus_corridors`.
- $S_{\text{transit}}$'s bonus redesigned into three independent, additive components per PRD §5.2 (`services/api/internal/scoring/factor_transit.go`), replacing the earlier flat "+10 for dual-line OR high-frequency bus" rule: dual-line access stays a flat +10 (transfer/redundancy proxy, unchanged); bus directional coverage now awards +10 for a qualifying high-frequency corridor in one direction, +15 if corridors cover both N-S and E-W (via the same `ST_Azimuth`/`isNorthSouthAzimuth` classification `S_bike` already uses); and a new 0-20 pt rail service-quality bonus blends AM-peak and overnight headway (linear decay, 6-20 min and 15-30 min bands) for the best-scoring line reachable within 1.0 mi, reading from `cta_line_service`. All three bonuses stack (previously capped as a single +10) and clamp with the base score to [0, 100].

- `S_solar` scored South (100/100) for every address searched through the new Address Search Input, regardless of the building's real orientation. Root cause, found via live testing against real `GET /api/v1/geocode` responses (not the hand-typed address strings `orientation_test.go` previously used exclusively): `InferStreetFacingOrientation` (`services/api/internal/scoring/orientation.go`) assumed the house number always leads the address string, but Nominatim's real `formattedAddress` prefixes a landmark/POI name before the house number for well-known buildings (e.g. `"Willis Tower, 233, South Wacker Drive, ..."` for 233 S Wacker Dr) — the regex never matched, silently falling back to the South default. A second bug surfaced fixing the first: once the house number parsed correctly, `detectStreetAxis`'s diagonal-street regex was matched against the *entire* remaining address rather than just the street segment, and Cook County's real "South Chicago Township" administrative name false-matched the pattern meant for South Chicago Ave, misclassifying the address as a diagonal street. Fixed with `stripLeadingNonNumericSegments` (finds the first purely-numeric comma-segment rather than assuming position 0) and `scopeToStreetSegment` (bounds classification to the house-number segment plus the immediate next one, dropping the rest of the admin hierarchy). New test cases in `orientation_test.go` use real, live-fetched Nominatim response strings rather than synthetic ones. Also switches `AddressSearchInput.tsx` to score by `address: candidate.formattedAddress` instead of `origin: candidate.coordinates` — `S_solar`'s orientation inference only runs when the request carries an address string at all, so `origin`-only requests skipped it entirely.
- The map card's rounded corners (`packages/web/src/App.tsx`) weren't actually rounded on the right edge in Chrome, and not rounded at all in Firefox/Zen. Two separate causes: the `lg:col-span-8` grid item had no `min-w-0`, so the MapLibre WebGL canvas's intrinsic content size could force the CSS Grid track wider than the viewport, pushing the card's right edge (and its rounded corner) off-screen past `<main>`'s padding; and Firefox renders that same WebGL canvas on its own GPU-composited layer, which its `overflow: hidden` + `border-radius` clipping never reaches — a long-standing Gecko limitation ([Mozilla Bugzilla #915492](https://bugzilla.mozilla.org/show_bug.cgi?id=915492), [#537433](https://bugzilla.mozilla.org/show_bug.cgi?id=537433)) that Chrome/WebKit don't have. Fixed with `min-w-0` on the grid item plus an explicit `clip-path: inset(0 round 0.375rem)` on the card (matching `index.css`'s `--radius-lg` override, not `rounded-lg`'s unmodified Tailwind default), which is a real compositor-level clip Firefox does honor on canvas layers. Also bumps the app's card/interactive-control corner radius from `rounded-sm` to `rounded-lg` (`packages/web/src/components/ui/card.tsx`, `AddressSearchInput.tsx`) per design feedback; `AGENTS.md` §4 updated to document the new standard.
