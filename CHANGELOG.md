## [Unreleased]

### Added

- `S_third_place` scoring factor (PRD §5.4): cafes and fitness venues within a 0.5 mile radius, scored 100/75/40/0 by count and proximity, with independent cafes (vs. chain brands like Starbucks/Dunkin', via a maintained exclusion list) weighted separately from fitness venues per the PRD's benchmark tiers. Adds `internal/clients/places.go` (Google Places API (New) `searchNearby` client) and `internal/scoring/factor_third_places.go`, which fills the existing `cache_entries` grid cache (400m cells, 30-day TTL, keyed by coordinate per `PRIVACY_AND_DATA_HANDLING.md` — never the raw address) with `golang.org/x/sync/singleflight` deduplicating concurrent cache-fills for the same cell. A new `places_api_budget` table (migration `00015`) enforces a daily cap on Places API calls, atomically incremented in Postgres rather than in-process memory so the cap survives restarts/redeploys and holds correctly across multiple server instances; exceeding it degrades `S_third_place` to `null` for the rest of the day rather than erroring the score request. Adds `GOOGLE_PLACES_DAILY_BUDGET_CALLS` to `.env.example`.
- `S_commute` scoring factor (PRD §5.10): scores a rush-hour ("next Tuesday 8:30 AM", America/Chicago) door-to-door transit itinerary to an optional user-provided workplace destination, banded 100/85/55/25/0 by duration plus a +10 one-seat-ride bonus and a -15/transfer friction penalty beyond the first transfer. Adds `internal/clients/otp.go`, defining `Itinerary`/`Leg`/`Route` types shaped after OpenTripPlanner 2's real GTFS GraphQL API (`planConnection` query, verified against OTP2's own schema) — Phase 3 scope is these types plus `internal/scoring/factor_commute.go`'s interface and fixture-tested scoring logic only; the live GraphQL-calling client lands in Phase 6.
- `POST /api/v1/score` (PRD §5.1): the composite scoring endpoint, wiring all 9 always-active factor calculators (transit, bike, grocery, third place, green, noise, safety, flood, solar) plus `S_commute` through `internal/scoring/engine.go`. Resolves `address`/`destination` via the existing Nominatim geocoder (best-ranked candidate) or accepts pre-resolved `origin`/`destinationCoordinates` directly, rejects requests outside the City of Chicago boundary with 422 `OUT_OF_COVERAGE`, and returns 400 `VALIDATION_ERROR` for a missing/duplicated address-or-origin or destination-or-destinationCoordinates pair. `S_commute` is registered with a `nil` querier (no live OTP2 client exists until Phase 6): it correctly appears in the response as `degraded: true` whenever a destination is supplied, rather than silently vanishing, and `benchmarkCommutes` is an honest empty array until Phase 6 can compute real hub pills. Adds `api.ScoreEngine` (`internal/api/score_engine.go`), a narrow interface expressed in `api`-owned types so the `api` package can depend on the scoring result shape without importing `internal/scoring` directly — `internal/scoring` already imports `internal/api` for its own request/response types, so the reverse import would be a cycle; `cmd/server`'s new `scoreEngineAdapter` bridges the two. Verified live end-to-end against the real Postgres/PostGIS data, Nominatim, and Google Places API for a real Chicago address.

- Phase 1 monorepo scaffolding:
  - Root `Makefile`, `docker-compose.yml` (PostgreSQL 18 + PostGIS, OTP2 2.9.0 with `profiles: ["transit"]`), and GitHub Actions CI workflow (`.github/workflows/ci.yml`).
  - Go API backend skeleton in `services/api/` with Go 1.22+ `net/http` routing, `log/slog` JSON logging, and `/metrics` Prometheus endpoint.
  - React 19 + Vite 8 frontend skeleton in `packages/web/` with Bun package manager, Biome linter, Tailwind CSS v4 design tokens, `shadcn/ui` primitives, and Lineicons.
  - Dual-stack OpenAPI codegen pipeline: `oapi-codegen` for Go and `openapi-typescript` for TypeScript, wired into `make generate` and `make generate-check`.
- OpenAPI 3.1 contract (`docs/openapi.yaml`) for `POST /api/v1/score`, `GET /api/v1/geocode`, `GET /api/v1/isochrones`, and `GET /api/v1/health`.
- `S_bike` scoring factor (PRD §5.11): quality-tiered proximity to bike infrastructure (protected lanes, buffered lanes, greenways, marked shared lanes) plus a directional network bonus for north-south/east-west coverage. Adds `bike` to `WeightOverrides` and `ScoreResponse.factors` in the OpenAPI contract, and rebalances the default weight presets (PRD §3.4) to include it.
- Phase 2 PostGIS schema (`db/migrations/`): 13 `goose` migrations covering `city_boundary`, `cta_stops`, `bus_corridors`, `bike_routes`, `parks`, `osm_pois`, `noise_sources`, `fema_flood_zones`, `sewer_311_incidents`, `cpd_crimes`, `safety_grid_percentiles`, `spatial_grid_cache`, and `cache_entries`, informed by live verification against the real Chicago Data Portal datasets (see `docs/DATA_SOURCES.md`).
- `S_safety` crime taxonomy (PRD §5.9): `cpd_crimes.category` expanded from a `violent`/`property` split to four scored categories (`violent`, `sexual`, `property`, `nuisance`), with a fifth unscored "excluded" set dropped at ingestion. `safety_grid_percentiles` now stores raw per-category counts alongside the combined `penalty_score`. Full `primary_type`/`iucr` mapping verified against the live Chicago Data Portal API (see `docs/DATA_SOURCES.md` "Category coverage").
- Data ingestion CLI (`services/api/cmd/seed`), first working dataset: `--dataset=boundary` fetches Chicago's city limits from the Chicago Data Portal and loads it into `city_boundary`, replacing the table's single row on each run. Adds the generic building blocks every later dataset PR reuses: a Socrata (SODA) API client (`internal/clients`, `X-App-Token` auth) and a PostGIS connection pool (`internal/spatial`, via `pgx/v5`).
- Three more seed CLI datasets: `--dataset=cta` groups the Chicago Data Portal's per-directional-platform rows into one `cta_stops` row per physical station (unioning line flags); `--dataset=bike_routes` and `--dataset=parks` load their respective datasets directly via `ST_GeomFromGeoJSON`. `--all` now runs all four implemented datasets in one pass. Parks are also repaired with `ST_MakeValid()` on ingest — 11 of 617 source park boundaries (including Washington Park, Grant Park, and Lincoln Park) have self-intersecting rings, a real data-quality issue in the source shapefile, not an ingestion bug.
- `--dataset=crimes`: ingests the trailing 12 months of Chicago crime data (~225K rows) into `cpd_crimes`, classified via the `S_safety` taxonomy (PRD §5.9). Pages through the source via `id`-based keyset pagination rather than `$offset` (confirmed via Socrata's own docs and the dataset's column metadata — see `docs/DATA_SOURCES.md` "Crimes" "Pagination"). The full fetch happens before any database transaction opens, so the `TRUNCATE` + batched-insert transaction that follows is seconds long rather than spanning the ~80s, 45-request fetch. Rows with no coordinates (~0.03% of the source) are skipped; a `primary_type`/`iucr` combination outside the documented taxonomy is logged as unrecognized and skipped rather than guessed. `internal/clients.SODAClient.GetJSON` now retries transient failures (network errors, 429, 5xx) with exponential backoff, benefiting every dataset.
- `--dataset=osm_pois`: ingests supermarkets, convenience stores, and pharmacies into `osm_pois`, powering `S_grocery`. Uses the live Overpass API (`internal/clients/overpass.go`) rather than the originally-planned local `.osm.pbf` file + `ogr2ogr`, after live verification found the local path lost the source ID for 99.8% of way-mapped (building-outline) stores — a real, non-trivial gap, since 52% of Chicago's real supermarkets/pharmacies turned out to be way-mapped rather than node-mapped. See `docs/DATA_SOURCES.md` "OSM POIs" and `ARCHITECTURE.md` Decision Log row 26 for the full investigation. Adds `internal/cache`, a generic Postgres-backed (`cache_entries`) key-value cache with a TTL — used here to cache the Overpass response (24h) rather than a local file, chosen specifically for portability across deployment environments; the same table will back Phase 3's Google Places grid cache later.
- `--dataset=noise`: ingests CTA rapid-transit tracks, expressways, and arterial roads into `noise_sources`, powering `S_noise`. Also via Overpass (`out geom` for full line geometry). CTA track grade (elevated/at-grade/underground) is derived from `tunnel`/`bridge`/`layer` tags rather than the `railway=subway` tag itself, which turned out to be used for the whole CTA system regardless of actual grade — verified against all 1,842 real track ways, including a spot-check confirming a way literally named "South Side Elevated" classifies correctly as `elevated`, not `underground`. `noise_sources` also gains `lanes`/`maxspeed_mph`/`has_turn_lane` columns, captured now (best-effort, nullable) for a planned future `S_stroad` / Street Safety factor rather than requiring a re-ingest later — see PRD §5.6.
- `--dataset=flood_zones`: ingests FEMA's National Flood Hazard Layer into `fema_flood_zones`, powering `S_flood`'s base score. Requires `city_boundary` to already be populated (run `--dataset=boundary` first) and fails loudly rather than silently ingesting zero rows if it isn't. Uses FEMA's own live ArcGIS REST MapServer (`internal/clients/fema.go`, `hazards.fema.gov`) rather than a downloaded shapefile/GDB extract, verified end-to-end before committing to it over the bulk-download path. `FEMAClient.QueryLayer` pages adaptively, ordered by `OBJECTID` for a stable, non-overlapping sequence across pages — halving the attempted window size on a size-related 5xx and retrying the same offset — since NFHL's vertex-dense polygons hit a server-side response-size ceiling independent of the row-count limit, deterministically rather than transiently (confirmed live: the same offset failed at one page size and succeeded at a smaller one, every time). A rate limit (429) or network failure instead gets ordinary exponential backoff at the same window size, and `FEMAClient.Count` now retries transient failures too, matching `QueryLayer`. A real undocumented zone value, `FLD_ZONE = "OPEN WATER"` (marks literal water bodies, not a risk-rated parcel), is logged and skipped rather than guessed into the official 10-code standard, as is a duplicate `FLD_AR_ID` (defense in depth alongside the `OBJECTID` ordering). Flood zone polygons are also repaired with `ST_MakeValid()`, same as `parks.go` — 1 of 291 Chicago-area zones had a self-intersecting ring. See `docs/DATA_SOURCES.md` "Flood Zones" and `ARCHITECTURE.md` Decision Log row 27.
- `--dataset=sewer_311`: ingests trailing 24 months of 311 water/sewer backup complaints (`sr_type = 'Water in Basement Complaint'`) from the Chicago Data Portal (`v6vf-nfxy`) into `sewer_311_incidents`, powering the localized urban flood penalty in `S_flood` (PRD §5.7). Pages via `sr_number` keyset pagination (~25.8K rows across ~6 SODA requests, < 10s fetch). Filters out `duplicate = true` rows (~4.4% of records) which represent redundant citizen reports for the same ongoing incident, avoiding multiplied penalties for a single event. Missing coordinate rows (~0.04%, 12 rows) are skipped; valid rows are loaded via a single fast `TRUNCATE` + batch insert transaction. Tested live against PostgreSQL with verified GiST spatial index performance.
- `--dataset=safety_grid` (and `--dataset=derive`): derives the ~500m citywide crime penalty distribution into `safety_grid_percentiles`, powering $S_{\text{safety}}$ percentile normalization (PRD §5.9). Projects `city_boundary` to UTM Zone 16N (`EPSG:32616`) to generate 2,650 uniform 500m square cells via PostGIS `ST_SquareGrid`, joins ~225K records from `cpd_crimes`, sums category counts, calculates raw penalty scores, and computes cumulative distribution percentiles via `PERCENT_RANK()`. Implements a zero-downtime recompute pipeline (ARCHITECTURE §11.3) writing derivations into an `UNLOGGED` staging table before performing an atomic transactional swap (~20ms lock duration) to prevent blocking live scoring queries.
- `--dataset=bus_corridors` (and `--dataset=derive`): derives CTA bus corridor geometries and scheduled headways into `bus_corridors`, powering the $+10\text{ pt}$ bus proximity bonus in $S_{\text{transit}}$ (PRD §5.2) and full network rendering for Phase 4 map layers. Streams the official CTA Static GTFS Schedule archive (`google_transit.zip`) in-memory using Go standard library (`archive/zip` + `encoding/csv`), parses weekday active services (`calendar.txt`), and computes scheduled mean headways per route across active directions during the weekday AM rush hour window (7:00–9:00 AM) from `trips.txt` and `stop_times.txt`. Routes meeting the $\le 10\text{ min}$ mean headway threshold (112 of 125 routes in live CTA data) qualify as high-frequency corridors, while off-peak/night routes receive a `999.00` sentinel. Assembles physical alignments from `shapes.txt` into composite `MULTILINESTRING` geometries in WGS84 (`EPSG:4326`) `geography` for all 125 Chicago bus routes. Caches the raw GTFS zip in `cache_entries` (PostgreSQL) with a 90-day TTL matching CTA's quarterly seasonal schedule cycle, speeding up subsequent development seed runs to ~4 seconds while remaining stateless in ephemeral containers. Implements a zero-downtime recompute pipeline via `bus_corridors_staging` and an atomic transaction swap (~170ms lock duration).
- Outbound Nominatim geocoding client (`services/api/internal/clients/nominatim.go`): one-shot address geocoding returning ranked coordinate candidates, rate-limited to $\le 1\text{ req/sec}$ via `golang.org/x/time/rate` with exponential backoff on transient errors (429, 5xx) and compliant `User-Agent` headers per the Nominatim Usage Policy. Biases candidate queries to the greater Chicago metropolitan area via viewbox.
- PostGIS city boundary spatial check (`services/api/internal/spatial/boundary.go`): verifies whether coordinate pairs fall inside the `city_boundary` multi-polygon via `ST_Covers(geom::geometry, ST_SetSRID(ST_MakePoint(lon, lat), 4326))`, enabling early rejection of out-of-coverage scoring requests.
- `GET /api/v1/geocode` HTTP handler (`services/api/internal/api/handlers.go`): wires address resolution to the Nominatim client, returning typed OpenAPI `GeocodeResponse` candidates with input query validation.
- Scoring engine orchestrator and weight normalizer (`services/api/internal/scoring/engine.go`): coordinates concurrent factor calculations, dynamically normalizes active weights ($\sum w_i = 100\%$) across default presets (Remote Worker vs. Hybrid Commuter) and user overrides, implements graceful degradation for timed-out or missing factor data, and clamps sub-scores to $[0, 100]$.
- $S_{\text{solar}}$ solar exposure factor (`services/api/internal/scoring/factor_solar.go`): computes natural lighting quality from window orientation lookup (South 100 to North 40 with intermediate interpolations), exposure modifiers (street $1.0\times$, courtyard $0.65\times$, alley $0.50\times$), and floor level bonuses ($+5\text{ pts}$ per floor above floor 2).
- Automatic street-facing orientation inference (`services/api/internal/scoring/orientation.go`): automatically derives a building's true street-facing window direction from Chicago's 1909 Brennan address numbering system (odd numbers on East-West streets face North, even numbers face South; odd numbers on North-South streets face West, even numbers face East; with diagonal azimuth geometry) when unit-level metadata is omitted.
- $S_{\text{flood}}$ flood risk factor (`services/api/internal/scoring/factor_flood.go`): evaluates FEMA National Flood Hazard Layer polygon overlays (Zone X 100 pts vs. Zone A/AE 40 pts) and applies a localized urban sewer backup penalty ($-5\text{ pts}$ per 311 basement flooding complaint within $0.25\text{ mi}$ over trailing 24 months).
- $S_{\text{noise}}$ acoustic livability factor (`services/api/internal/scoring/factor_noise.go`): calculates cumulative proximity penalties from quiet street baseline (100 pts) for elevated/at-grade CTA tracks (-35 pts at < 150 ft, -20 pts at 150–300 ft; subways exempt), expressways (-30 pts at < 500 ft), and major 4-lane arterials (-15 pts at < 100 ft).
- $S_{\text{grocery}}$ grocery and daily retail factor (`services/api/internal/scoring/factor_grocery.go`): computes supermarket distance decay (100 pts at <= 0.3 mi, 75 pts at 0.3–0.75 mi, linear decay to 0 at 1.0 mi), corner store/convenience fallback (capped at 40 pts), and pharmacy bonus (+10 pts at <= 0.2 mi).
- $S_{\text{green}}$ green space and parks factor (`services/api/internal/scoring/factor_green.go`): evaluates geodesic distance to nearest park polygon boundary (100 pts at <= 0.1 mi, decaying to 50 pts at 0.3 mi and 0 pts at 0.75 mi) plus signature linear trail bonus (+15 pts for Lakefront Trail, The 606/Bloomingdale Trail, or `LINEAR PARK` at <= 0.25 mi).
- $S_{\text{safety}}$ public safety factor (`services/api/internal/scoring/factor_safety.go`): evaluates localized point-in-polygon crime incident density against precomputed citywide ~500m grid percentiles (`safety_grid_percentiles`), mapping relative safety percentiles cleanly to intuitive 0–100 scores (100.0 - percentile).
- $S_{\text{bike}}$ bike infrastructure factor (`services/api/internal/scoring/factor_bike.go`): calculates quality-tiered proximity decay to cycling infrastructure (100 pts for Protected Bike Lanes/Greenways, 70 pts for Buffered Lanes, 40 pts for Painted Lanes, 15 pts for Sharrows; decaying to 0 at 0.5 mi) and awards a +15 pt dual-axis network bonus for connectivity across both North-South and East-West corridors.
- $S_{\text{transit}}$ transit accessibility factor (`services/api/internal/scoring/factor_transit.go`): calculates distance decay to CTA 'L' rapid-transit stations (100 pts at <= 0.25 mi, linear decay to 0 pts at 1.0 mi) and awards a +10 pt bonus for dual-line station access (2+ distinct lines across stations within 1.0 mi) or high-frequency bus corridors (mean headway <= 10 min) within <= 0.2 mi.
- `cta_line_service` table (`db/migrations/00014_create_cta_line_service.sql`): one row per CTA 'L' line storing AM-peak and overnight mean headway, powering the revised $S_{\text{transit}}$ rail service-quality bonus (PRD §5.2).
- `--dataset=cta_line_service` (and `--dataset=derive`): derives per-line AM-peak and overnight headway into `cta_line_service` from the same CTA static GTFS feed already used for `bus_corridors` (`route_type = 1` rather than `3`), reusing its weekday-service parsing for the AM-peak pass and adding a new any-day-of-week (but still validity-window-filtered) pass for the 1:00-4:00 AM overnight window per PRD §5.2. `line_name` is derived from `route_long_name` (e.g. `"Red Line"` → `"Red"`) rather than `route_id`, which is inconsistently formatted across lines. The overnight pass weights each contributing `service_id` by how many nights per week it actually runs (`computeOvernightHeadwaysByLine`) rather than naively summing trips across every weekday/Saturday/Sunday template — CTA's real feed splits overnight service into several such templates per line, and summing them unweighted inflated a single night's trip count by up to ~3x (caught in review before merge; see `docs/DATA_SOURCES.md` "CTA Line Service" for the live-verified numbers). No staging-table swap (8 rows, no geometry) and no `geom` column, unlike `bus_corridors`.
- $S_{\text{transit}}$'s bonus redesigned into three independent, additive components per PRD §5.2 (`services/api/internal/scoring/factor_transit.go`), replacing the earlier flat "+10 for dual-line OR high-frequency bus" rule: dual-line access stays a flat +10 (transfer/redundancy proxy, unchanged); bus directional coverage now awards +10 for a qualifying high-frequency corridor in one direction, +15 if corridors cover both N-S and E-W (via the same `ST_Azimuth`/`isNorthSouthAzimuth` classification `S_bike` already uses); and a new 0-20 pt rail service-quality bonus blends AM-peak and overnight headway (linear decay, 6-20 min and 15-30 min bands) for the best-scoring line reachable within 1.0 mi, reading from `cta_line_service`. All three bonuses stack (previously capped as a single +10) and clamp with the base score to [0, 100].

### Fixed

- `.env.example`'s `DATABASE_URL` had the database name and password swapped relative to `docker-compose.yml`'s actual `POSTGRES_DB`/`POSTGRES_PASSWORD` values, which would have caused `make migrate-up` and the API's own DB connection to fail with an auth error.
- `docker-compose.yml`'s `db` service mounted the `pgdata` volume at `/var/lib/postgresql/data`, which PostgreSQL 18+ images no longer use — the `postgis/postgis:18-3.6-alpine` image expects the volume at `/var/lib/postgresql`, and the container would fail its healthcheck and error-loop indefinitely without this.
- `bus_corridors`' GTFS headway derivation (`cmd/seed/bus_corridors.go`) pooled trips across multiple back-to-back `service_id` schedule "seasons" instead of only the one currently valid, since it filtered `calendar.txt` by day-of-week flags alone with no `start_date`/`end_date` check — CTA's live feed republishes a near-identical weekday schedule under a new `service_id` roughly every 2-4 weeks (132 of 133 live routes affected), so every computed `mean_headway_minutes` was roughly half of what any single real day actually runs. Caught before any deployment while building the `cta_line_service` derivation below. See `ARCHITECTURE.md` Decision Log row 28.
