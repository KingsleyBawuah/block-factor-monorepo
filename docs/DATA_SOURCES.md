## Overview

This document records the *real, verified* shape of each external dataset BlockFactor ingests — actual field names, resource IDs, and category values pulled directly from the live source, not assumptions from the PRD/ARCHITECTURE prose. It exists because a first pass at designing the Phase 2 migration schemas from documentation alone produced several wrong assumptions, caught only by querying the real APIs. Update this doc whenever a new dataset is investigated, before writing the migration or ingestion parser for it.

**Caution:** search engines and AI-generated summaries can fabricate plausible-looking resource IDs. One showed up in this investigation (`3w5d-sru8` for bike routes) that does not exist in any actual source link — only in a search tool's synthesized prose. Resource IDs below were confirmed by actually querying `https://data.cityofchicago.org/resource/{id}.json`, not by trusting search summaries.

## Chicago Data Portal (SODA API) Datasets

### CTA 'L' Stops
- **Resource ID:** `8pix-ypme` ("CTA - System Information - List of 'L' Stops")
- **Real structure:** One row **per directional platform**, not per station. E.g. `"18th (54th/Cermak-bound)"` and `"18th (Loop-bound)"` are two separate rows (`stop_id` 30162 and 30161) for the same physical station.
- **Key fields:** `stop_id`, `station_name` (shared across a station's directional rows), `stop_name` (directional), `map_id` (groups directional rows into one station), `ada` (boolean), individual boolean columns per line: `red`, `blue`, `g` (green), `brn` (brown), `p` (purple), `y` (yellow), `pnk` (pink), `o` (orange). Coordinates via `location.latitude`/`location.longitude`.
- **Schema decision:** Ingest by grouping on `map_id`, computing a `lines TEXT[]` array from whichever boolean columns are true, storing **one row per station** — not the raw per-direction shape. Avoids double-counting in any future "count nearby stations" logic and avoids duplicate overlapping map markers in Phase 4.

### CTA 'L' Lines
- **Resource ID:** `xbyr-jnvx` ("CTA - 'L' (Rail) Lines") — confirmed live via `https://data.cityofchicago.org/resource/xbyr-jnvx.json` (153 rows). Distinct from `8pix-ypme` (stations, already ingested as `cta_stops`) and from `t9su-47fb`/`m3d6-pubu` (a rendered map view and a deprecated KML export of the same underlying data — neither queried, not needed).
- **Key fields:** `the_geom` (MultiLineString), `lines` (free-text, comma-separated list of line names sharing this track segment), `type` (`Subway` or `Elevated or At Grade` — 21 vs. 132 of 153 rows, verified via a full group-by), `legend` (short internal code, e.g. `ML`, `BR`, `YL` — undocumented, not used for parsing), `description` (human station-to-station span, e.g. `"Tower 12 to Library"`), `shape_len`.
- **Real `lines` values are messy** (verified via a full group-by, 16 distinct values across all 153 rows): the same "express" modifier is abbreviated two different ways — `"Purple (Express)"` and `"Purple (Exp)"` both occur. Parsing must normalize both to one express flag, not string-match a single spelling. Full distinct set: `Blue Line (Forest Park)`, `Blue Line (O'Hare)`, `Brown Line`, `Brown, Green, Orange, Pink, Purple (Exp)`, `Brown, Orange, Pink, Purple (Express)`, `Brown, Purple`, `Brown, Purple (Express), Red`, `Green Line`, `Green, Orange`, `Green, Pink`, `Orange Line`, `Pink Line`, `Purple Line`, `Red Line`, `Red, Purple Line`, `Yellow Line`.
- **Schema decision:** parse `lines` into a `TEXT[]` matching `cta_stops.lines`'s vocabulary (`Red`, `Blue`, `Brown`, `Green`, `Orange`, `Pink`, `Purple`, `Yellow` — strip the `" Line"` / `" (Forest Park)"` / `" (O'Hare)"` suffixes, same normalization approach `cta_line_service` already applies to `route_long_name`), plus a separate `express BOOLEAN` derived from the `(Express)`/`(Exp)` modifier rather than folding it into the line name. `type` maps to a `grade TEXT` column (`'subway'` or `'elevated_or_at_grade'`) — coarser than `noise_sources`'s three-way `underground`/`elevated`/`at_grade` split (that dataset derives grade from `bridge`/`tunnel`/`layer` tags; this one's `type` field can't distinguish elevated from at-grade), so don't conflate the two grade vocabularies when writing the map layer endpoint.
- **Purpose:** Powers the Phase 4 CTA Rail map layer (`docs/IMPLEMENTATION_PHASES.md` Phase 4) — the only real per-line rail track geometry source found. `noise_sources`'s CTA track ways are explicitly line-agnostic (its Overpass query filters by CTA operator only, not by individual line — see "Noise Sources" below), so they can't be colored per official CTA line color.

### Crimes
- **Resource ID:** `ijzp-q8t2` ("Crimes - 2001 to Present")
- **Key fields:** `id` (Socrata's stable unique row ID — use this as `source_id`, not `case_number`), `date` (full ISO timestamp, not a bare date), `primary_type` (free text, e.g. `"BATTERY"`, `"CRIMINAL DAMAGE"` — not a violent/property flag), `iucr` and `fbi_code` (the actual classification codes with established violent/property mapping tables), `latitude`/`longitude`.
- **Schema decision:** Store the raw `primary_type` and `iucr` alongside our own derived `category` column — don't discard the source classification, since the mapping logic may need auditing or refinement later. Use `crime_date` as `TIMESTAMPTZ`, not `DATE`.
- **Data quality notes from live investigation:**
  - `CRIM SEXUAL ASSAULT` and `CRIMINAL SEXUAL ASSAULT` are the same real-world offense recorded under two different labels at different points in the dataset's 25-year history — both must map to the same category.
  - `OTHER OFFENSE` and `OFFENSE INVOLVING CHILDREN` are IUCR catch-all `primary_type` values that bundle dozens of unrelated `iucr` sub-codes — mapping them correctly requires grouping by `iucr`/`description`, not just `primary_type`. `RITUALISM` and `DOMESTIC VIOLENCE` are effectively dead legacy codes (24 and 1 record total since 2001, 0 in the trailing 12 months) but still need a safe bucket for stray historical rows.
- **Category coverage:** `cpd_crimes.category` is `NOT NULL CHECK (category IN ('violent', 'sexual', 'property', 'nuisance'))` — a fifth, unscored "excluded" set of real `primary_type`/`iucr` values is intentionally dropped by the ingestion CLI before insert rather than stored, since `S_safety` (PRD §5.9) only scores the four categories below. This is a deliberate ingestion-time filter, not an oversight. Full mapping, verified via live group-by queries against the SODA API (trailing-12-month volumes shown):

  | Category | Weight | `primary_type` values | Notable `iucr` sub-codes (under `OTHER OFFENSE` / `OFFENSE INVOLVING CHILDREN`) |
  |---|---|---|---|
  | **Violent** | 5× | Homicide, Assault, Battery, Robbery, Kidnapping, Human Trafficking, Domestic Violence, Weapons Violation, Concealed Carry License Violation, Stalking, Intimidation | Non-sexual child abuse/endangerment/abandonment/abduction (1750, 1710, 1755, 1790, 1780), Animal Abuse/Neglect (501A), Abuse/Neglect - Care Facility (500N), Animal Fighting (1682), Other Crime Against Person (5000), Telephone Threat/Harassment (2820, 2825, 2826, 2830), Order-of-Protection/No-Contact/GPS-monitoring violations (4386, 4387, 4388, 4389), Gun/Violent Offender/Arsonist registration failures (5110, 5111, 5112, 5130, 5131, 5132, 5121), Other Weapons Violation (5007), Board Plane with Weapon (4860), Unlawful Use of Body Armor (4740) |
  | **Sexual** | 5× | Criminal Sexual Assault (incl. legacy `CRIM SEXUAL ASSAULT` spelling), Sex Offense | Family-member child sexual abuse/assault (1751, 1752, 1753, 1754), Child pornography/distribution/possession (1582, 1519, 1726, 1537), Sex Offender registration failures (4650, 4651, 4652) |
  | **Property** | 1× | Theft, Burglary, Motor Vehicle Theft, Criminal Damage, Arson, Criminal Trespass | Stolen/altered temp plate, vehicle title/registration fraud, vehicle tampering (502P, 5002, 502R, 502T), Other Crime Involving Property (5001), Possession of Burglary Tools (4310), Other Arson/Explosive Incident (5003) |
  | **Nuisance** | 2× | Narcotics, Other Narcotic Violation, Prostitution, Public Peace Violation, Public Indecency, Obscenity, Interference with Public Officer | — |
  | *Excluded (unscored, dropped at ingestion)* | — | Gambling, Non-Criminal, Liquor Law Violation, Deceptive Practice, Ritualism | License Violation (5011), Eavesdropping (500E), Money Laundering (4800), Smoking Ban Violation (5009), Parole/Probation Violation (4625, 4510), Summary Closure Violation (5013), Hazardous Materials Violation (501H), Internet Offenses - Electronic Fencing (1147), Contribute to (Criminal) Delinquency of Child (1720, 1725), Harbor Runaway (1791) |

  This taxonomy and the 5×/5×/1×/2× weighting were worked out collaboratively (not a purely mechanical FBI UCR mapping) — see PRD §5.9 for the reasoning per category. Any `iucr` sub-code not listed above and not covered by a top-level `primary_type` row falls to the ingestion CLI's judgment; extend this table when a new one is encountered rather than guessing silently. `5121` (Arsonist registration) was found and added during the crimes parser build by re-running the same live group-by queries — it follows the established pattern that offender-registration-failure codes inherit the category of the underlying offense they register for, same as the Gun/Violent/Sex Offender codes already in this table.
- **Pagination:** trailing 12 months is ~225K rows — far past SODA's 1000-row default page cap. Socrata's own docs recommend filtering over deep `$offset` paging (performance degrades as the offset grows), and the internal `:id` field doesn't support `>` comparisons for this dataset. The real `id` column is declared `number` type in the dataset's own metadata (confirmed via `/api/views/ijzp-q8t2.json`), so the ingestion CLI pages via `id`-based keyset pagination (`ORDER BY id`, `WHERE id > <last seen>`) instead — O(1) per page regardless of depth, rather than degrading like `$offset` does.
- **Null coordinates:** ~0.03% of trailing-12-month rows (62 of 225,034 at time of writing) have no `latitude`/`longitude` at all — skewed toward `THEFT` and `DECEPTIVE PRACTICE` (fraud-type reports with no physical crime scene to geocode), spread across many districts with no single systemic cause. Since `cpd_crimes.geom` is `NOT NULL`, these rows are skipped at ingestion rather than inserted with a fabricated location.
- **Confirmed live/current:** sample pulled during this investigation included records from the current week, confirming the "updated daily" claim in ARCHITECTURE §11.2.

### Bike Routes
- **Resource ID:** `hvv9-38ut` (current). **Not** `3w5d-sru8` — that ID was a search-summary hallucination; it doesn't appear in any real result link. Deprecated prior versions exist at `2u3n-4ewv` (2014) and `8ec2-eaj2` (2021) — don't use those either.
- **Key fields:** `the_geom` (MultiLineString), `displayrou` (the actual category field), `street`, `st_name`, `f_street`/`t_street` (from/to cross streets), `mi_ctrline` (segment mileage).
- **Real `displayrou` categories** (verified via a full group-by count, not a sample): `Neighborhood Greenway`, `Buffered Bike Lane`, `Bike Lane`, `Protected Bike Lane`, `Marked Shared Lane`. **None of these is "trail"** — this dataset is street-based bike infrastructure only; it does not include the Lakefront Trail or 606.
- **Schema decision (pending):** originally assumed as map-only decoration (Phase 4) with a simplistic `protected_lane`/`trail` category split. Being reconsidered as a real scored factor (`S_bike`) given the real quality gradient across these 5 categories — see the in-progress PRD update.

### Parks
- **Resource ID:** `ejsh-fztr` ("CPD_Parks" — the actual populated dataset). **Not** `ej32-qgdr` ("Parks - Chicago Park District Park Boundaries (current)") or `xjk8-wnm8` ("parks") — both returned empty geometry/properties on every query despite HTTP 200 responses; likely stale/orphaned catalog entries despite their titles.
- **Key fields:** `the_geom` (Polygon/MultiPolygon), `park` (name), `park_no`, `park_class`, `acres`, `shape_area`, plus a large number of shapefile-truncated amenity boolean columns (`dog_friend`, `basketball`, `tennis_cou`, etc. — DBF 10-character field name limit artifacts).
- **Real `park_class` values:** `NEIGHBORHOOD PARK`, `COMMUNITY PARK`, `REGIONAL PARK`, `MINI-PARK`, `PASSIVE PARK`, `NATURE PRESERVE PARK`, `UNIMPROVED PARK`, `PARKWAY PARK`, `MAGNET PARK`, **`LINEAR PARK`** (22 rows), `CITYWIDE PARK`, `PARKWAYS PARK`, `PENDING` (unresolved classification — a real data-quality gap to handle gracefully, not error on).
- **Schema decision:** `LINEAR PARK` is almost certainly where The 606/Bloomingdale Trail and Lakefront Trail segments actually live in the data. PRD 5.5's "off-street trail access point" bonus should be computed from `parks WHERE park_class = 'LINEAR PARK'`, not from `bike_routes` — these are two separate datasets that had been conflated under one "trail" concept.
- **Data quality note:** 11 of 617 source polygons have self-intersecting rings (`ST_IsValid` fails) — a real defect in the source shapefile's largest, most complex boundaries (Washington Park, Grant Park, Lincoln Park, Humboldt Park, and others), confirmed by auditing the ingested data, not an ingestion bug. 3 of the 11 are `LINEAR PARK` rows (Major Taylor Bike Trail, Sauganash Trail, Midway Plaisance), so this isn't cosmetic — it would have affected `S_green`'s off-street trail bonus. The ingestion CLI repairs these with `ST_MakeValid()` before insert.

### City Boundary
- **Resource ID:** `qqq8-j68g` ("Boundaries - City")
- **Key fields:** `the_geom` (MultiPolygon GeoJSON), `shape_area`.
- **Confirmed matches original assumption** — no schema changes needed.

### 311 Service Requests (sewer/water backup)
- **Resource ID:** `v6vf-nfxy` ("311 Service Requests" — the unified post-2018 system; a `legacy_record` column flags older pre-2018 rows folded in).
- **Confirmed real `sr_type` value:** `"Water in Basement Complaint"` — exact string match needed for ingestion filtering. Powers the sewer backup penalty half of `S_flood` (PRD §5.7).
- **Key fields:** `sr_number` (unique service request ID used as `source_id`), `created_date` (SODA floating timestamp, stripped of fractional seconds), `duplicate` (boolean), `latitude`/`longitude` (WGS84 EPSG:4326).
- **Duplicate filtering:** 1,180 of ~27K trailing 24-month rows (4.4%) have `duplicate = true`, referencing a `parent_sr_number`. Auditing parent/child pairs (e.g. `SR19-01327672` and `SR19-01329269` at 2325 E 68th St) confirmed that `duplicate = true` marks subsequent citizen calls for the *same ongoing basement flooding event* at the same property. Ingestion filters to `duplicate = false` so that multiple calls for a single event do not multiply the local flood penalty.
- **Pagination & Volume:** Trailing 24 months contains ~25.8K records. Paged via `sr_number` keyset pagination (`ORDER BY sr_number`, `WHERE sr_number > <last_seen>`) with page size 5,000 (~6 HTTP requests).
- **Missing coordinates:** ~0.04% of trailing-24-month rows (12 of 25,773) lack `latitude`/`longitude` and are skipped at ingestion. Ingests ~25.7K rows in < 1 minute.

## OpenStreetMap Datasets

### OSM POIs (Supermarkets, Convenience Stores, Pharmacies)

Powers `S_grocery` (PRD 5.3). This dataset's ingestion path changed mid-investigation — recorded here in full because the reasoning matters for revisiting it later, not just the final answer.

- **Originally planned:** download the Geofabrik Illinois `.osm.pbf` extract (`https://download.geofabrik.de/north-america/us/illinois-latest.osm.pbf`, ~342 MB) and shell out to `ogr2ogr` locally, per the ARCHITECTURE §13.2 tooling decision (Decision Log row 25). Verified live: GDAL's OSM driver's `points` layer (node-mapped POIs — a single pushpin per store) worked cleanly — 2,007 Illinois-wide candidates, all with real IDs, real coordinates, real recognizable stores (Whole Foods, Jewel-Osco, CVS, Walgreens).
- **Where that plan broke down:** many real stores are mapped as a traced building outline (a "way" in OSM's data model — see `docs/GIS_GLOSSARY.md` "Node / Way / Relation") rather than a single node. GDAL's `multipolygons` layer, which is supposed to assemble those into usable polygons, returned 3,534 Illinois-wide candidates for the same tags — but **3,528 of them (99.8%) had `osm_id: null`**. GDAL's way-assembly step hit topologically imperfect ways/relations somewhere in its processing (its own warnings: "non-closed ring," "organizePolygons() received an unexpected geometry... return arguments as a collection") and fell back to synthesizing best-effort geometry that lost the traceable source ID in the process. Since `osm_pois.source_id` is `NOT NULL UNIQUE` — the mechanism a re-sync uses to recognize "have I seen this store before" — rows with no real ID aren't usable without inventing synthetic IDs, which risks silent duplicates on the next quarterly sync.
- **Confirmed this is a GDAL-conversion problem, not an OSM data problem:** queried the same way-mapped stores directly against the **Overpass API** (`overpass-api.de`, a live, purpose-built OSM query service — a different tool than local PBF processing) and got back real, permanent, stable way IDs for all of them — e.g. Jewel-Osco at 5343 N Broadway, Chicago is `way/28357149`; Aldi at 4500 N Broadway is `way/33972029`. The underlying OpenStreetMap database has always had real IDs for these; GDAL's local `.pbf`-to-simple-features conversion step is what loses them, because it has to re-interpret OSM's native node/way/relation graph into flat GIS polygons, and that re-interpretation is GDAL's own best-effort process, not how OSM stores the data. Overpass reads the native graph model directly and never hits this problem.
- **Decision: switched entirely to the Overpass API** (`internal/clients/overpass.go`) for this dataset — both nodes and ways, in one combined query, rather than local PBF + `ogr2ogr`. This is a deliberate departure from the ARCHITECTURE §13.2 tooling decision as originally resolved (Decision Log row 25) for this one dataset specifically; `ogr2ogr` remains the right call for the shapefile-based datasets (bike routes, parks already done; FEMA NFHL still pending) since those don't hit this way-ID problem at all.
- **Concrete impact, verified against a real Chicago-wide run:** of 1,111 POIs that landed inside Chicago's actual boundary, **581 (52%) are way-mapped** — Cermak Fresh Market, Aldi, 88 Marketplace, Supermercado El Güero, Whole Foods, and many more real, well-known stores that the original node-only plan would have silently missed entirely. This was first noticed via a live cross-check against Pilsen (Chicago's "Lower West Side" community area, OSM relation `10099447`) at the user's request — roughly half of Pilsen's real supermarkets, including Aldi, were way-mapped and absent from the node-only result set.
- **Query design:** one combined query for all three tag categories (`shop=supermarket`, `shop=convenience`, `amenity=pharmacy`; both `node` and `way`), against a bounding box derived from our own `city_boundary` geometry (`ST_YMin`/`ST_XMin`/`ST_YMax`/`ST_XMax`), not a name-based OSM administrative area — keeps this consistent with how the rest of the system determines "is this in Chicago" (the `OUT_OF_COVERAGE` hard-reject). The bbox necessarily over-fetches (it's a rectangle around an irregular, two-ring city shape — Chicago's `city_boundary` has 2 rings, the main body plus O'Hare's detached exclave, confirmed via `ST_NumGeometries`), so precise Chicago-limits filtering happens at insert time via `ST_Covers` against `city_boundary`, not in the Overpass query itself. `out tags center` computes a representable point for way results server-side — no centroid math needed on our end. Verified live: 1,674 bbox candidates → 1,111 actually inside Chicago's real boundary, 0 invalid geometries, 0 duplicate `source_id`s, 0 unclassifiable tags.
- **`source_id` format:** `"node/<id>"` or `"way/<id>"` (matching OSM's own URL convention, e.g. `openstreetmap.org/way/28357149`) — necessary because OSM node IDs and way IDs are separate ID spaces and could otherwise collide (a node and a way could both legitimately have ID `12345`).
- **Known minor nuance, not fixed:** a small number of real stores appear to be double-mapped — the same physical place represented as both a node and a way (e.g. a `BP Shop` and a `Gas N Wash` found ~3m and ~131m apart respectively, same name, different OSM types, in the Pilsen sample). Measured at 3 likely pairs out of 1,674 candidates (~0.18%) — small enough that building fuzzy-match deduplication for it isn't worth the complexity right now, but worth knowing it's there rather than assuming every row is a distinct physical location. (Not every same-name-nearby pair is actually a duplicate — e.g. a supermarket's building outline and a separately-tagged in-store pharmacy node are both real, distinct amenities worth counting separately, not a duplicate to collapse.)
- **Post-ingestion spot-check, 4 neighborhoods:** beyond the aggregate row counts above, cross-checked the actual ingested `osm_pois` rows against fresh live Overpass queries for four real Chicago community areas, chosen for geographic/demographic spread rather than convenience — Pilsen/Lower West Side (relation `10099447`), Hyde Park (`9884770`, South Side, near the University of Chicago — note "Hyde Park" is a common name shared by unrelated places worldwide, including a Wisconsin hamlet and neighborhoods in St. Louis and Cincinnati; confirmed the right one via its `wikipedia` tag, `en:Hyde Park, Chicago`), Logan Square (`10110588`, Northwest Side), and Rogers Park (`122575`, Far North Side lakefront). Every one of the 78 live candidates across the three latter neighborhoods (Pilsen's numbers are above) was present in `osm_pois` with the correct `poi_type` — 0 missing, 0 misclassified, including recognizable real stores (Trader Joe's and Whole Foods in Hyde Park, Aldi and Mariano's Fresh Market in Logan Square, Jewel-Osco in Rogers Park).
- **Sign-up / auth:** none required for the public `overpass-api.de` instance used here (confirmed against Overpass's own docs) — some *other* Overpass mirrors (Geofabrik's own, FairwayMapper) do require API keys/subscriptions, but that's not the one in use. Courtesy requirement instead: a `User-Agent` header identifying the application, set on every request.
- **Rate limits:** the documented fair-use ceiling that causes server strain is ~10,000 requests/day from abusive/commercial traffic patterns. This dataset syncs quarterly (one combined query per run) — nowhere near that ceiling. The retry-with-backoff in `OverpassClient.Query` (mirroring `SODAClient.GetJSON`) handles ordinary transient 429/5xx responses; it is not a rate-limit-avoidance mechanism, since our actual request volume was never the risk.
- **Caching:** the raw Overpass response is cached in `cache_entries` (24h TTL) via the new `internal/cache` package — not a local file. This was a deliberate choice raised directly by a deployment-portability concern: a local file cache would silently stop working (or behave inconsistently) in an ephemeral-compute deployment model (e.g. containers/Lambdas with no persistent disk between invocations), whereas `cache_entries` lives in the same Postgres instance the ingestion CLI already has to reach to do its job, so the same code path works identically regardless of where it runs. In practice, this also means dev and production never need different code paths: a quarterly production run is always past the 24h TTL and always fetches live, while repeated local `make seed` runs during development reuse the cached response. `internal/cache` is deliberately generic (not OSM-specific) since Phase 3's Google Places grid-cache client (ARCHITECTURE 5.4, 30-day TTL) will reuse the same table and the same `Get`/`Set` pattern.

### Noise Sources (CTA Tracks, Expressways, Arterials)

Powers `S_noise` (PRD 5.6). Also queried via Overpass (same client, same bounding box, same `cache_entries` caching pattern as OSM POIs above), but with `out geom` instead of `out center` to get each way's full line geometry rather than a single point.

- **CTA tracks — a real tagging surprise:** every CTA rapid-transit track way is tagged `railway=subway` (filtered via `way["railway"="subway"]["operator"~"Chicago Transit Authority",i]`), **regardless of whether it's actually underground**. A way literally named "South Side Elevated" — `bridge=yes`, `layer=2` — is tagged `railway=subway` the same as a genuinely underground segment. In OSM, `railway=subway` apparently denotes "this is a rapid-transit rail system" generically, not "this specific segment is underground." Grade is derived separately from `tunnel`/`bridge`/`layer` tags instead (exactly the approach PRD 5.6 already specified before this was verified: *"grade separation is derived from OSM `bridge` / `tunnel` tags"*): `tunnel` set → `underground`; `bridge` set → `elevated`; neither → `at_grade`, with `layer`'s sign as a fallback for the ~1% of ways (18 of 1,842) that carry a `layer` tag but no explicit `tunnel`/`bridge` tag. Verified against every one of the 1,842 real CTA track ways in Chicago: 931 at-grade, 760 elevated, 151 underground. Spot-checked "South Side Elevated" specifically post-ingestion — correctly classified `elevated`, not `underground`.
- **Expressways:** `highway=motorway` — confirmed against every named Chicago expressway (Kennedy, Dan Ryan, Stevenson), matching PRD 5.6's own examples ("Expressways (I-90/94, I-290, etc.)") exactly.
- **Arterials:** `highway=primary` only, deliberately **not** `secondary`. `secondary` roads in Chicago span a much wider, less consistent lane range (1–7 lanes in a live sample) with heavy missing `lanes`-tag coverage (~40%), making it a weaker match for PRD 5.6's "Major 4-lane Arterial Corridors" than `primary`. Not hard-filtering on `lanes ≥ 4` either, for the same missing-data reason — a real major street lacking a `lanes` tag would otherwise be silently excluded, which is worse for a livability tool than being slightly loose.
- **`lanes`/`maxspeed_mph`/`has_turn_lane` metadata (new columns):** captured from OSM at ingestion time for every source, even though no scoring logic uses them yet — see PRD 5.6's `S_stroad` / Street Safety callout. `maxspeed` is consistently formatted `"NN mph"` in this dataset (378/378 sampled, 0 exceptions) — a simple regex parse, no unit-conversion ambiguity found. `lanes:both_ways` (OSM's dedicated tag for a continuous center turn lane) is **not used anywhere in the Chicago dataset** (0 occurrences sampled), so `has_turn_lane` instead checks any `turn:lanes*` tag for a `left` value — a real, verified signal, but one that describes a specific way *segment* near an intersection, not a claim that the whole corridor has a continuous turn lane. All three are nullable/best-effort: `lanes` and `maxspeed_mph` are absent on a real share of Chicago roads (arterial: 88%/51% coverage; expressway: 99%/84%), and CTA tracks legitimately have neither (`lanes` and `turn:lanes` are road-only OSM tags, not applicable to rail — confirmed 0 coverage for tracks, which is correct, not a bug).
- **Query volume:** one combined query (all three categories together) — 8,352 candidates in the Chicago bbox, ~15s live fetch. Noticeably heavier than OSM POIs' query despite similar candidate count, since `out geom` returns every intermediate coordinate along each way rather than one point.

## FEMA Datasets

### Flood Zones

Powers `S_flood`'s base score (PRD 5.7). The zone letter codes themselves (`A`, `AE`, `AH`, `AO`, `AR`, `A99`, `V`, `VE`, `X`, `D`) are FEMA's fixed, published national standard, already confirmed against FEMA's own glossary before the migration was written — this section is about the *ingestion path*, which turned out to have real surprises of its own.

- **Live REST API instead of a shapefile/GDB download:** FEMA's National Flood Hazard Layer (NFHL) is served as a live, public ArcGIS REST MapServer at `hazards.fema.gov/arcgis/rest/services/public/NFHL/MapServer` — no sign-up, GeoJSON output supported directly (`f=geojson`). Layer **28, "Flood Hazard Zones"**, is the one that matters here — confirmed against the service's own layer list (layer 3 "FIRM Panels" is just the map-sheet index, not hazard data; layers 1/34 are Letters of Map Revision/Amendment, unrelated to zone risk). Chose this over FEMA's bulk shapefile/GDB download (available via the Map Service Center, `msc.fema.gov`) because the REST path was fully verified end-to-end — real field names, real zone codes, a confirmed true total count — while the bulk-download portal is JavaScript-driven and couldn't be reliably checked by automation without guessing a URL, something this doc already explicitly warns against.
- **Real field names:** `FLD_AR_ID` (a stable, confirmed-unique feature ID — used as `source_id`) and `FLD_ZONE` (the actual zone letter code, e.g. `"X"`, `"AE"`). Confirmed via the layer's own field list (`.../28?f=json`), not assumed from the zone-code standard alone.
- **A real value outside the official 10-code standard:** `FLD_ZONE = "OPEN WATER"` showed up in live Chicago data — it marks literal water bodies (e.g. Lake Michigan itself), not a risk-rated land parcel, so it isn't part of FEMA's published risk-zone glossary. Logged and skipped at ingestion rather than guessed into one of the ten official codes or silently dropped without a trace — same "recognized-but-not-a-real-risk-zone" pattern as crimes' excluded category.
- **A real response-size ceiling, independent of the row-count limit — and it's deterministic, not transient:** the service's own `maxRecordCount` is 2000, but NFHL polygons are extremely vertex-dense (one 50-record window returned **15MB**), so a fixed page size fails unpredictably depending on which specific polygons happen to fall in a given page — confirmed live that the *same* offset fails at a larger record count and succeeds at a smaller one, every time, not intermittently. A naive fixed page size (even one already confirmed to work in general, like 200) isn't reliable on its own. `FEMAClient.QueryLayer` instead pages adaptively: on a retryable failure, it halves the attempted window size and retries the *same* offset (down to a confirmed-safe floor of 5 records) rather than blindly retrying an identical doomed request. Verified live: two separate offsets in Chicago's data needed shrinking (one down to 37, one down to 18) before the full, confirmed 2,541-feature total was fetched successfully.
- **Total count confirmed, not assumed:** `returnCountOnly=true` gives the real total (2,541 for Chicago's bounding box) upfront, so pagination has an exact, unambiguous stopping condition — important specifically because adaptive window sizing means "a page came back shorter than requested" can't reliably signal "this is the last page" here, unlike the fixed-page-size datasets (crimes, OSM POIs).
- **Self-intersecting geometry — same class of defect found in Chicago's own park boundaries:** 1 of 291 Chicago-area flood zone polygons failed `ST_IsValid()`. Fixed the same way as `parks.go`: `ST_MakeValid()` before `ST_Multi()`, applied to both the inserted value and the `ST_Intersects` boundary check (an invalid input can make that predicate unreliable too, not just the stored geometry).
- **`ST_Intersects`, not `ST_Covers`, for the Chicago-boundary filter:** unlike `osm_pois`' single points, a flood zone polygon can legitimately straddle the city line — flood risk follows floodplain/waterway geography, not administrative boundaries. `ST_Covers` (fully contained) would wrongly drop zones that meaningfully affect Chicago addresses near the edge; `ST_Intersects` (any overlap) is the correct predicate. Of 2,541 candidates in the (necessarily loose, rectangular) bounding box, 291 actually intersect Chicago's real boundary — the high exclusion rate (88%) is expected, not a bug: the bbox necessarily covers a lot of suburban Cook County land (Evanston, Oak Park, Cicero, etc.) that sits inside the rectangle but outside city limits.
- **Caching:** same `cache_entries`-backed `internal/cache` pattern as OSM POIs/noise sources, 24h TTL — reused for consistency rather than picked bespoke, since the TTL's real job is bounding repeated local `make seed` runs during development, not tracking how often FEMA's real data changes (official flood map revisions are years apart, far slower than OSM). One difference from the single-request OSM POIs/noise pattern: since this dataset needs multi-page fetching, all pages are assembled into one combined feature list first, then the *combined* result is cached under one key — same "check cache → miss → fetch → cache → use" shape, just with pagination happening inside the fetch step.

## Derived Datasets

### Safety Percentile Grid (`safety_grid_percentiles`)

Powers $S_{\text{safety}}$ percentile normalization (PRD §5.9). Fully derived from `cpd_crimes` and `city_boundary` during seed/derivation (`--dataset=safety_grid` or `--dataset=derive`).

- **Grid Resolution:** 500m $\times$ 500m square cells (~0.25 km²). Generated by transforming `city_boundary` into UTM Zone 16N (`EPSG:32616`, exact meter projection) via `ST_SquareGrid(500, geom_proj)`, filtering for intersection with Chicago limits, and transforming back to WGS84 (`EPSG:4326`) `geography`. Yields 2,650 grid cells covering the entire municipal boundary.
- **Penalty Calculation:**
  $$\text{Penalty} = (5 \times \text{Violent}) + (5 \times \text{Sexual}) + (1 \times \text{Property}) + (2 \times \text{Nuisance})$$
- **Percentile Ranking:** Evaluated across all 2,650 cells using PostgreSQL's `PERCENT_RANK() OVER (ORDER BY penalty_score ASC) * 100`. The safest cells (penalty = 0, ~13.4% of city cells representing parks/forest preserves/lakefront margins) evaluate to 0.00 percentile. The highest-crime downtown commercial blocks evaluate to 100.00 percentile.
- **Zero-Downtime Recompute:** To prevent long exclusive locks on live scoring queries during re-derivation, the spatial join across ~225K crimes and percentile calculations are written into an `UNLOGGED` staging table (`safety_grid_percentiles_staging`, ~2.4s compute time). An atomic transaction then executes `TRUNCATE safety_grid_percentiles; INSERT INTO safety_grid_percentiles ...; DROP TABLE safety_grid_percentiles_staging;` committing in ~20ms.

### Bus Corridors (`bus_corridors`)

Powers the $+10\text{ pt}$ high-frequency bus proximity bonus in $S_{\text{transit}}$ (PRD §5.2) and powers full transit route rendering for Phase 4 map layers. Fully derived from the official CTA Static GTFS Schedule archive (`google_transit.zip`) during seed/derivation (`--dataset=bus_corridors` or `--dataset=derive`).

- **Headway Derivation:** Parses `calendar.txt` to isolate regular weekday service (`monday=1 ... friday=1`) that is also currently within that `service_id`'s `start_date`/`end_date` validity window as of the day the seed CLI runs, filters `routes.txt` for bus routes (`route_type = 3`), and computes the mean scheduled headway per route across active directions during the weekday AM rush hour window (07:00:00 to 09:00:00, 120 minutes) from `trips.txt` and `stop_times.txt`. Routes with a mean scheduled headway $\le 10.0\text{ minutes}$ qualify as high-frequency corridors (112 of 125 routes in live CTA data). Routes with zero AM rush trips (e.g. Night Owl routes or midday tourist shuttles) receive a `999.00` sentinel headway.
  > **The validity-window check matters:** CTA's feed republishes a near-identical weekday schedule under a new back-to-back `service_id` roughly every 2-4 weeks (132 of 133 live routes reference 2+ such blocks). Without checking `start_date`/`end_date`, trips from multiple sequential schedule "seasons" get pooled together as if they all ran on the same calendar day, silently doubling counted trips and halving every computed headway. See `ARCHITECTURE.md` Decision Log row 28 for the full investigation, including why the original test suite couldn't catch it.
- **Corridor Geometry:** Assembles the physical street alignments from `shapes.txt` for all route shape variations into composite `MULTILINESTRING` geometries stored as WGS84 (`EPSG:4326`) `geography`. All 125 Chicago bus routes are stored with their respective headways and complete street network geometries.
- **In-Memory Streaming & Caching:** The seed CLI streams the zipped CSVs in-process with Go's standard library (`archive/zip` + `encoding/csv`), requiring zero temporary disk files and keeping memory usage under ~150MB. The raw ~100MB `.zip` is cached in `cache_entries` (PostgreSQL) with a 90-day TTL matching CTA's quarterly seasonal schedule refresh cycle, speeding up subsequent development seed runs to ~4 seconds while maintaining zero external state in ephemeral containers.
- **Zero-Downtime Recompute:** Built into an `UNLOGGED` staging table (`bus_corridors_staging`) before performing an atomic transactional swap into `bus_corridors` (~170ms lock duration).

### CTA Line Service (`cta_line_service`)

Powers the rail service-quality bonus in $S_{\text{transit}}$ (PRD §5.2). Derived from the same CTA Static GTFS Schedule archive as `bus_corridors` during seed/derivation (`--dataset=cta_line_service` or `--dataset=derive`) — the cached `.zip` (`cache_entries`, key `cta:gtfs:zip`) is shared between both derivations, so running one after the other doesn't re-download or re-cache anything.

- **Line Identification:** Filters `routes.txt` for rail routes (`route_type = 1`). `route_id` itself is inconsistent across lines (`Red`, `Blue`, `Pink` use the full word; `Purple`, `Yellow`, `Green`, `Orange`, `Brown` use single/short codes — `P`, `Y`, `G`, `Org`, `Brn`), so `line_name` is instead derived from `route_long_name` minus its trailing `" Line"` suffix (e.g. `"Red Line"` → `"Red"`), which matches `cta_stops.lines`' vocabulary exactly and was verified directly against the live feed.
- **AM-Peak Headway:** Same methodology and validity-window filtering as `bus_corridors` above (weekday, 07:00-09:00, currently-valid `service_id`s only) — reuses the same `parseCalendarServices`/`parseTrips` helpers rather than a second implementation.
- **Overnight Headway:** Mean scheduled headway during 1:00-4:00 AM, matched against calendar service_ids that are date-valid but with no day-of-week filter (PRD §5.2 defines this window as "any day"). GTFS represents late-night trips in two conventions — same-day (`01:00:00`-`03:59:59`) and after-midnight (`25:00:00`-`27:59:59`, for a trip whose `service_id` represents the previous calendar day) — both confirmed present in the live feed and handled without double-counting (a departure matches at most one representation). Lines with zero matching trips (Yellow, in live CTA data) store `NULL` rather than a sentinel, matching the schema design in `db/migrations/00014_create_cta_line_service.sql`.
  > **Day-of-week weighting matters here:** CTA's real feed splits overnight service into several separate `service_id` templates per line — not just one weekday/Saturday/Sunday split, but finer patterns too (e.g. a live-verified "Monday only" template plus a separate "Tuesday-Saturday" template covering the same 1:00-2:45 AM portion). Naively summing first-departures across every matching `service_id` and dividing by the 3-hour window — treating a 5-night/week template the same as a 1-night/week template — inflates a single night's trip count by up to ~3x and deflates the computed headway by the same factor. `computeOvernightHeadwaysByLine` instead weights each `service_id`'s contribution by its `daysPerWeek` and divides by 7 to get a true trips-per-night average, matching the standard "typical night" headway a rider would actually expect. Verified against live data: Red Line's naive/unweighted figure was 5.0 min; the correct day-weighted figure is 15.0 min, matching its real published overnight service.
- **No Geometry:** Unlike `bus_corridors`, this table has no `geom` column — headway is a line-level property, not a place.
- **No Staging-Table Swap:** 8 rows with no geometry already gives a plain `BEGIN; TRUNCATE; INSERT; COMMIT` an effectively-zero lock duration, so the zero-downtime staging pattern used by `bus_corridors`/`safety_grid_percentiles` would be pure overhead here.
